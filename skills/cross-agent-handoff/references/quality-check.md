# 交出与接收质量检查

交出前检查草稿；接收时按需要核对。这里是证据检查，不是要求额外搭建任务管理系统。

- 当前目标、阶段、授权范围、实际项目根与停止条件清楚；所有引用在接收端可访问或已标缺失。
- Done 有实际文件/结果证据并标明不要重复；计划和已生成文件不能冒充已执行或已验证。
- 决定包含选择理由；失败尝试记录观察结果、实际错误及证据。原因只是推断时明确标出；没有失败不能为填表编造。
- 未完工作、待答问题与阻塞可区分；保留用户未决问题的原意，说明它是否阻塞下一步。
- 接收端核对现场后，只有一个立即业务动作。验证命令、预期结果和停止条件单列；已经结束就不安排新任务。
- 分支/HEAD/相关未提交与未跟踪文件、测试适用版本来自实际检查。无 Git、unborn、detached、未知均可合法表达；不能把空 diff 当干净。
- 受测代码与记录相符；有新变动、失败或疑点才补相关验证。代码已变而旧测试尚未复跑时保留原记录并标明不再适用。
- 不包含凭据、无关私人/公司内容、整段私有会话。必要错误片段先去敏感内容；原始历史读取没有另行授权就不做。
- 不留未填写占位符；写前重读已有入口，保留仍有效的信息和他人改动。先保存证据再引用，计划中的收尾材料不能冒充已有文件；写后确认实际文件与链接。
- 只有一份项目当前状态；验收报告、旧日志和快照是证据，不另立另一平台的进度事实源。
- 源文件可读、宿主原生加载、独立接续、真实生命周期事件分别给结果；没有事件回执不能用一次手动交接代替。

接收端修改前，应能根据这些材料说明“做了什么、为什么这样做、哪条路失败、什么仍未解决、唯一下一步”。如果解释依赖没保存的历史，先说明缺口；关键缺口影响结果时再询问。
